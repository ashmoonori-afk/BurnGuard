# Platform packages and graphic sets — 2026-09-10

This is the implementation record for the plan in [doc/14](./14-deliverables-and-platform-publishing-plan-2026-09-09.md) and the decisions in [ADR-015](./07-decisions.md#adr-015-deliverable-kinds-platform-packages-and-additive-brief-fields). Multi-frame graphic deliverables, long product-detail exports, multi-page site awareness, and guided Cafe24 (카페24) and Imweb (아임웹) packages ship without a new project type, a stored credential, or an automatic deployment path. Paths below are the integration-branch paths; the work landed across three implementation branches and is described as one tree.

Every external platform figure in this record keeps the verification status it carries in doc/14 section 13. Where a figure is labelled "not verified" here, it is a warning threshold in code, never a hard rule, and no real shop was used to confirm it.

## Behavior and boundaries

A website project keeps loose `.html` files; the site map is always derived, never persisted. Ordering is entrypoint first, then shared-navigation order, then alphabetical, capped at 24 pages with the overflow reported rather than hidden (`packages/backend/src/services/site-map.ts:6,46,66-67`). Creation briefs accept at most 12 pages (`packages/shared/src/design-brief.ts:36`). Pages duplicate their chrome inside marked shared blocks and split their CSS into shared and page sections; a project without the markers falls back to landmarks and gains an advisory finding instead of failing. Site findings are advisory, so an HTML ZIP still exports; platform packages gate on their own lint. Page rename and move remain unavailable. The chat payload carries `active_rel_path`, validated against the session's own project files before prompt assembly (`packages/backend/src/routes/session.ts:160,195`); the prompt then emits the active page and the site map with missing targets marked `MISSING`.

Graphic deliverables are kinds of the existing graphic project: `single`, `card_news`, `product_detail`, `banner_set`, `thumbnail`, and `print`. Frame count is bounded 1–40, a BurnGuard resource limit rather than a verified vendor limit. Only `banner_set` may carry per-frame sizes, and only `product_detail` may carry the seven detail-brief fields; supplying either on the wrong kind is a typed contract error. Presets carry a confidence flag and a checked date. Verified presets are the Meta and Instagram feed, carousel, and story sizes; the Naver GFA, Kakao, marketplace, YouTube, and print-working-area entries are not verified and produce warnings only. Presets below the 320x240 canvas minimum cannot be selected as a canvas size.

`png_zip` is available for a slide deck, a graphic set with more than one frame, or a product-detail page. Deck and frame sets are captured per artboard in document order, and the rendered artboard count must match the declared frame count. Product-detail pages are sliced instead: cut points land on top-level `[data-bg-node-id]` section bottoms that fit within `slice_height` (3,000 or 5,000), a forced cut records a `cut_through_content` finding, and each slice stays inside a 16,000,000-pixel budget with a hard slice-count limit. `slice_format` may be `jpeg` for product-detail exports only, with `jpeg_quality` between 60 and 95 (default 85, a BurnGuard default with no vendor source); JPEG output is decoded and its dimensions checked before publication. Marketplace byte caps of 20 MB and 5 MB come from third-party pages and are not verified; the exporter enforces pixel and dimension budgets, not vendor byte caps.

Artboard PDF prints one page per artboard at the artboard size in points, with print CSS that removes stacked-layout spacing so no blank pages appear. A set whose frames differ in size has no single page geometry and is rejected with a typed error; the export menu disables the option for such sets rather than producing a wrong document.

The Cafe24 package targets classic Smart Design (스마트디자인) only; Smart Design Easy is reported as unsupported. The archive contains `layout/burnguard-layout.html` with exactly one contents marker, one `pages/<page>.html` fragment per page opening with the layout directive, the rewritten asset tree under `web/<slug>/`, `GUIDE.html`, `lint.json`, and `burnguard-export.json`. Assets are addressed through `asset_base_url`, defaulting to the root-relative `/web/upload/burnguard/<slug>/`; that serving path is not verified. The shop's own `layout.html` is never touched, because editing it propagates to every screen. Bundled fonts travel with their license notices; WOFF2 is outside the uploader allowlist reported by an unverified source, so it produces a warning and no format conversion. Every Cafe24 finding is a warning, including duplicate jQuery, oversized files, folders over 1,000 files, non-ASCII asset filenames, and unresolved inter-page links.

The Imweb package produces one code-widget fragment per page plus `common/header-code.html` and `common/footer-code.html`. Fragments carry no document wrapper and no shared navigation, because Imweb owns site navigation. CSS is scoped under a single class with PostCSS, and an explicit heading and paragraph reset is prepended because the code widget is not style-isolated. HTML comments are stripped, since the editor removes them on save. A fragment over 1,000,000 characters is a blocking error; 500,000 characters is a warning. Images at or under the inline budget are embedded as data URIs, larger images need a hosted URL, and a missing one raises `imweb_image_needs_hosting` with the documented board-attachment workaround. Imweb packages default to a system-font fallback stack and emit no Google Fonts link; this is the recorded exception to the runtime font policy in doc/05.

Packages ship only what the entrypoint's static closure and the site map reference, so private material such as `docs/attachments` never enters an archive. The transformed archive is validated independently of the source closure: entry digests, package-relative paths, required roles, the layout directive, the single contents marker, and an allowlist of generated external URLs. The receipt binds the package to the project digest, the options digest, and a transformation version.

The full lint inventory is one module (`packages/backend/src/services/platform-lint.ts:4-14`). Cafe24 warnings: `cafe24_disallowed_extension`, `cafe24_file_over_30mb`, `cafe24_folder_over_1000_files`, `cafe24_korean_asset_filename`, `cafe24_jquery_duplicate`; Cafe24 info: `cafe24_unresolved_link`. Imweb error: `imweb_page_over_1m_chars`, which fails the export as `platform_lint_failed` with stop reason `validation_failed`; Imweb warnings: `imweb_page_over_500k_chars`, `imweb_local_font`, `imweb_form_or_iframe`, `imweb_image_needs_hosting`, `imweb_global_selector`, `imweb_duplicate_id`, `imweb_document_script`. One cross-platform warning, `platform_dynamic_reference`, reports references no rewriter can follow.

Nothing is uploaded anywhere. A finished export is labelled "패키지 다운로드됨" with an explicit note that it is not yet published, and the in-app guide renders static guide strings, never HTML read back from the archive. Every guide step carries its own verified or unverified status.

Two fixes landed alongside this work. The quality panel now derives an `idle` state with retry enabled instead of an endless spinner when the audit query settles with no report and no error (`packages/frontend/src/lib/design-audit-state.ts`). The canvas frame bridge intercepts only `.html` and directory-style links, mirroring `resolveCanvasPageTarget`, so asset and external links keep their default behavior (`packages/frontend/src/components/canvas/frame-bridge.ts`).
