# BurnGuard browser E2E coverage report (2026-09-12)

Local verification for branch `feat/pointer-comment-shortcut-20260912`, PR #53. This report records browser behavior and its evidence boundaries, not a public deployment or merge.

This report maps every row of the feature inventory (`/tmp/burnguard-feature-inventory.md`, written before any browser run) to the browser scenario that now covers it, or to the exact reason it can't be covered here. Screenshots and per-check JSON stay in the `/tmp` evidence directories and aren't committed.

## 1. How to read the evidence

### Boundary labels

Each scenario carries a `mode` string in its `results.json`. They collapse into five boundaries:

| Label | Meaning |
|---|---|
| **LIVE** | Real browser driving an isolated BurnGuard backend with its own temporary home, port and fixture data. Feature modules use installed Chrome 152; the complete legacy suite uses Playwright 1.59.1's matched Chromium 147 because of the independently reproduced Chrome 152 input-routing issue in section 4. Files, SQLite, IndexedDB and downloads are inspected directly. |
| **CODEX** | Same as LIVE, but the run passed `--live-auth yes` and the backend spawned the real, authenticated Codex CLI (0.153.2, ChatGPT login). Paid turns are budgeted per run. |
| **PUBLIC-RO** | Real outbound HTTPS reads from public sources (website, GitHub, `.git`, one Pinterest pin). Read only; nothing was written externally. |
| **MOCK** | Real DOM and real backend, but a specific API response, stream event or provider boundary was replaced with a synthetic one (`M-*`, `synthetic-*`, `controlled-transport`, `explicit-http-fixture`). Recovery after the fault is still real. |
| **PENDING / BLOCKED / NOT TESTED** | Not proven in this cycle. The reason is stated per row. |

### Runners and commands

Legacy suite (43 named scenarios, core plus fixture groups):

```sh
node scripts/qa/e2e-smoke.mjs --channel chrome --port 14173 --shots /tmp/<dir> [--only core|review-R26|creation-canvas|deliverables-]
```

The successful integrated command used the separately installed matching browser:

```sh
PLAYWRIGHT_BROWSERS_PATH=/tmp/burnguard-fixture-browsers \
  node packages/backend/node_modules/playwright-core/cli.js install chromium-headless-shell
PLAYWRIGHT_BROWSERS_PATH=/tmp/burnguard-fixture-browsers \
  node scripts/qa/e2e-smoke.mjs --channel bundled --port 14175 \
  --shots /tmp/burnguard-full-bundled-final
```

Install the browser matching the project's Playwright version into your chosen cache before using `--channel bundled`; the path above is this run's disposable cache.

The new deck sandbox test also uses the matched browser. Other existing browser unit tests use installed Chrome. The final root command is:

```sh
PLAYWRIGHT_BROWSERS_PATH=/tmp/burnguard-fixture-browsers bun test --timeout 30000
```

Full-feature modules, one process per module, isolated backend and Chrome, cleanup receipt in `cleanup.json`:

```sh
node scripts/qa/full-feature-runner.mjs --module scripts/qa/<module>.mjs --port <port> --evidence /tmp/<dir> [--live-auth yes]
```

Without `--live-auth yes` the runner points `CODEX_HOME` and `CLAUDE_CONFIG_DIR` at empty owned directories, so no real account can be used by accident. Creation's original graphic-template check and the graphics module require that flag for authenticated readiness but send no provider turn. Generation and AI-entrypoint modules require it for their bounded real turns; the FIFO interruption fixture requires a POSIX host. `full-export-features.mjs` additionally requires `BG_EXPORT_QA=1`. `full-ai-entrypoints.mjs` is also directly executable and spawns the runner itself.

To include both controlled local acquisition cases in the 32-case catalog run:

```sh
SOURCE_ORIGIN=http://127.0.0.1:14222
BG_EXTRACTION_QA_ADAPTER_SOURCE_URL="$SOURCE_ORIGIN/source" \
BG_EXTRACTION_QA_ADAPTER_STALL_URL="$SOURCE_ORIGIN/stall" \
BG_EXTRACTION_QA_ADAPTER_RESOURCE_URLS="$SOURCE_ORIGIN/source,$SOURCE_ORIGIN/stall,$SOURCE_ORIGIN/styles.css,$SOURCE_ORIGIN/brand-logo.svg" \
BG_EXTRACTION_QA_ADAPTER_SECRET="$(openssl rand -hex 32)" \
node scripts/qa/full-feature-runner.mjs \
  --module scripts/qa/full-catalog-features.mjs --port 14202 \
  --evidence /tmp/catalog-verification
```

## 4. Browser-version boundary and integrated result

An earlier full Chrome 152 run failed `creation-canvas-prototype-subpages` despite passing alone and inside `--only creation-canvas` (10/10). The read-only diagnosis (`/tmp/st_01a09647-report.md`) established the following.

What was shown, with high confidence:

- Playwright acknowledged the locator click, and trusted `pointerdown`/`mousedown`/`pointerup`/`mouseup`/`click` fired, but every one of them targeted the parent document's `<iframe>` element. The srcdoc child recorded `events=[]`; the bridge's navigation listener and the early QA capture listener were both installed (confirmed through CDP `DOMDebugger.getEventListeners`) and never invoked.
- A Chrome trace shows the mouse events dispatched in the parent renderer (`WidgetInputHandlerImpl::DispatchEvent` in PID 66645) while the child renderer (PID 68292) was alive, compositing, and received no input dispatch.
- Application-side explanations were excluded by captured React props: `mode: null`, iframe `pointer-events: auto`, all tool overlays `pointer-events: none`, `elementsFromPoint` returning the iframe first. `uiStore` holds no canvas mode.
- An app-free reproduction (owned HTTP server, plain srcdoc iframe with inert overlay siblings, real Chrome) reproduced the same all-events-on-parent pattern at navigation 30 and 41 of a loop, with no React or BurnGuard code loaded. This is a native Chromium out-of-process-iframe input-routing race on a long-lived Page.
- Reproduction is intermittent: three diagnostic full runs failed the target twice and passed it once.

What was not established:

- The exact Chromium internal state or scheduling trigger behind the misrouting.
- Whether any Chrome version, Playwright version, or launch flag fixes it universally. Playwright 1.63.0 and removing the `RenderDocument` override each passed the target once and then failed a different iframe-link case; the app-free reproduction still failed at navigation 108 under the second variant.

The controlled Page-isolation experiment passed all 10 creation-canvas cases, but a following old-Page deliverables link failed. Subsequent Chrome 152 runs with every independent group on a fresh Page also showed intermittent R26 input failure, so isolation is not claimed as a universal fix. The harness retains group isolation, original order, native input and every assertion; it also removes invalid early-document toast observation and waits for history mutations to settle.

The final complete run used the project's matched Chromium 147 and passed **43/43** at `/tmp/burnguard-full-bundled-final/results.json`, including R26, subpages, directory links, Cafe24 export and quality review. Feature-specific modules, including the strengthened 119-case graphics run, use Chrome 152 separately. Temporary click injection and React-fiber inspection were removed. No force-click, evaluated-click, retry or reordered scenario was used to turn the integrated result green.
